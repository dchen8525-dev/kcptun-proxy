## 2. 部署前修掉的一处缺陷

`-h` 里服务端示例写成 `-b 0.0.0.0:4462`（空格分隔），而本程序的值参数**必须** `--name=VALUE`，照抄会直接报错。已改为 `-b=0.0.0.0:4462`，并新增 `TestUsageExamplesAreRunnable`：把 server/client 帮助里的示例命令行拆成参数喂给 `Parse`，防止帮助文本与解析器再次漂移。

`scripts/check.sh` 全绿后重新 `build.sh`，得到新产物 sha256 `c31032c30fabca04ccf2610bed73935c5d4be19ee1002af4039d768f0efeb796`（旧 `aed31174…` 作废）。

## 3. 实际执行的部署命令

```bash
cd /d/work/kcptun-proxy

# 1) 上传到临时路径，先校验再安装（避免半截文件被 systemd 拉起）
scp dist/kcptun-server-linux-amd64 your-vps:/tmp/kcptun-server.new
ssh your-vps 'sha256sum /tmp/kcptun-server.new; file /tmp/kcptun-server.new'
# 远端：c31032c3…  ELF 64-bit LSB executable, x86-64, statically linked, stripped
# 远端权限 -rw-r--r--，直接执行失败 → 证实 NTFS 执行位确实丢了

scp deploy/kcptun-server.service your-vps:/tmp/kcptun-server.service
ssh your-vps '
  install -m 0755 /tmp/kcptun-server.new      /usr/local/bin/kcptun-server
  install -m 0600 /tmp/kcptun-server.service  /etc/systemd/system/kcptun-server.service
  rm -f /tmp/kcptun-server.new /tmp/kcptun-server.service
  systemctl daemon-reload
  systemctl enable --now kcptun-server
'
```

`deploy/kcptun-server.service` 的实际 ExecStart：

```
/usr/local/bin/kcptun-server --key=00112233445566778899aabbccddeeff \
  -b=0.0.0.0:4462 --fec=10:3 --mtu=1400 --log-level=info
```

- `Restart=always` / `RestartSec=2` / `LimitNOFILE=65535`，stdout(stats) 与 stderr(日志) 都进 journal（沿用 `fcp-node.service` 风格）。
- 单元文件权限 `0600`，因为 PSK 内联其中；相比 `fcp-node.service` 的 0644 收紧了一点。
- `--fec` / `--mtu` 显式写出而不依赖默认值：本实现无参数协商，两端必须逐字一致，默认值将来变动不该静默改变已部署行为。

### 真实链路吞吐

测速源：VPS 上 `systemd-run --unit=kcptun-bench --collect node /tmp/kcptun-bench.cjs`（`scripts/bench-source.cjs`，32 MiB 全内存），监听 `127.0.0.1:18080`。本机经 SOCKS5 下载；`socks5h` 让 `127.0.0.1` 在 **VPS 侧**解析，所以测的是「本机 ↔ VPS」这一段隧道，不含 VPS 到第三方 CDN 的波动。VPS 本地直连该源 32 MiB / 0.043 s，不是瓶颈。

首轮（kcptun-proxy 单独，32 MiB ×3）：**2.65 / 1.26 / 2.45 MB/s**，`12.68 / 26.63 / 13.67 s`。

同时间窗口交替复测（两个 client 同时在线，A/B/A/B/A/B）：

| run | kcptun-proxy (UDP 4462) | fcp-node (UDP 4461) |
| --- | --- | --- |
| 1 | 1,715,456 B/s (19.56 s) | 2,745,711 B/s (12.22 s) |
| 2 | 1,690,716 B/s (19.85 s) | 3,323,959 B/s (10.09 s) |
| 3 | 1,510,058 B/s (22.22 s) | 2,621,041 B/s (12.80 s) |

fcp-node 日志佐证其参数：`FCP PMTUD: path carries 1500B (ceiling reached, started at 1040B)`、`FCP established: D=10 P=6 tlv=true ackv2=true mtu=1040->1500 (pmtud)`。

IP 分片：`/proc/net/snmp` 的 `Ip:` 行，测前 `ReasmReqds=0 ReasmFails=0 FragCreates=0`，测后 `reqds=0 oks=0 fails=0 fragOK=0 fragFail=0 fragCreate=0`。

### 结论与边界

- **环回结论反转**：本机环回 kcptun-proxy 59.6 MB/s 是 fcp-node 12.1 MB/s 的 4.9×；同一条真实 VPS 链路上反过来慢约 1.8×。这正是 README 原先「真实链路要重测，结论可能反过来」的验证，不是新发现的实现回归。
- **归因未定**：候选差异是 PMTUD（1500B vs 固定 1400B）、自适应 FEC（10:6 vs 固定 10:3）、BBR-lite vs kcp-go fast3 `nc=1`（关拥塞控制）、SACK v2。本次**没有做消融实验**，不能把差距归因到任何单项。分片计数为 0 只排除 IP 层分片，不排除 UDP 层丢包/重传（当前 stats 只统计应用层字节，看不到重传量）。
- RTT 依据：部署前 `ping -n 2 vps.example.com` 为 229 / 271 ms。
- 吞吐波动大（首轮 1.26–2.65 MB/s），跨洋链路本身抖动明显，三次采样不足以给出置信区间；上表只作量级参考。

## 5. 运维与回滚

```bash
ssh your-vps 'systemctl status kcptun-server --no-pager -l'
ssh your-vps 'journalctl -u kcptun-server -f'          # stats 行 + 日志
ssh your-vps 'systemctl restart kcptun-server'
ssh your-vps 'systemctl stop kcptun-server'             # 停服；disable 另需 systemctl disable
```

升级：`scp` 新二进制到 `/usr/local/bin/kcptun-server`（`install -m 0755` 保留执行位）后 `systemctl restart kcptun-server`。**改 `--fec` / `--mtu` 必须同时改客户端**，否则连不上或静默丢包。

回滚：`systemctl disable --now kcptun-server`，删除 `/etc/systemd/system/kcptun-server.service` 与 `/usr/local/bin/kcptun-server`，`systemctl daemon-reload`。fcp-node 全程独立，回滚不影响它。
